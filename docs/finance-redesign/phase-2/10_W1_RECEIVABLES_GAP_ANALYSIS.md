# 10 — W1 Receivables: Current-vs-Target Gap Analysis (Read-Only)

Read-only analysis comparing the WNG-confirmed W1 decisions (`03_WNG_FINANCE_DECISION_REGISTER.md`,
confirmed 2026-09-23) against the current codebase. **No code changed as a result of this
document.** Facts are drawn from the Phase 1 audit (`current-state/05_CURRENT_WORKFLOWS.md`,
`current-state/07_APPROVAL_AND_PERMISSION_MATRIX.md`) and re-confirmed directly against source
where cited. This is input to Phase 2B, not a build plan.

Classification key: **ALREADY SUPPORTED** / **PARTIALLY SUPPORTED** / **NOT SUPPORTED** / **BLOCKED
BY OTHER DECISION**.

| Decision | WNG Requirement | Current Behaviour | Gap | Future Change Required | Dependency |
|---|---|---|---|---|---|
| W1-1 | Preparer ≠ checker; checker may issue; roles: Project Officer (billing info), Accounts Preparer, Accounts Reviewer/Finance Approver | Any Project Officer/Accounts user can both create and issue a client invoice with zero mandatory review — `07_APPROVAL_AND_PERMISSION_MATRIX.md` §13.4 confirms the Approval Matrix's Reviewer column is empty for Client Invoice; posting is gated only on the accounting period being open, not on any human check | **NOT SUPPORTED.** No "checked by"/"checked at" concept exists on `ProjectInvoice`; no permission separates "prepare" from "check/issue"; no server-side rule prevents the same user from preparing and issuing | Add a review/check status and timestamp to the invoice lifecycle (`draft` → `checked` → `issued`, or a checked-at/checked-by pair alongside existing statuses); add a permission gating the check/issue step, distinct from creation; add a same-user guard (preparer ≠ checker) mirroring the pattern already used elsewhere (SpendVoucher, Payroll) | **BLOCKED BY ROLE-1** — needs the functional-role-to-permission mapping decided before the permission itself can be named/built |

## What this means for Phase 2B

- ROLE-1 (the functional-role-to-real-position mapping) blocks the permission-layer half of W1-1
  and W1-6. Everything else in W1 can, in principle, be designed and built independently of ROLE-1,
  though it will be cleaner to sequence ROLE-1 first since three separate decisions depend on it.
- W1-3/W1-4/W1-9's target figures are largely a presentation exercise over data that is already
  correct — the underlying ledger/allocation logic does not need to change for these three.
- W1-2, W1-7, and W1-8 each require a genuine new data-model element (an exception record, a
  payment-terms table, a discount column) that does not exist in any form today.
- W1-5's permission-level requirement is already met; only the explicit audit-field pairing needs
  confirming against what `07_APPROVAL_AND_PERMISSION_MATRIX.md` §22 already found about the
  existing audit-trail mechanisms, before assuming new columns are needed.
